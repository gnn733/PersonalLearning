# RAG 之后的 Agent 学习路线

更新日期：2026-10-15。

[返回 Agent 分类](README.md) · [LangGraph 分步学习](langgraph-study-guide.md) · [教程与项目清单](advanced-resources.md)

## 先明确下一步

完成基础 RAG 后，可以开始学 LangGraph。基础 RAG 的完成标准是：自己能加载资料、切分、入库、检索、回答，能检查来源并定位简单错误。

RAG 是为回答补充外部资料的方法；LangGraph 用来组织有状态、多步骤、可分支或循环的执行流程。检索可以成为图中的一个节点，也可以成为 Agent 调用的工具。使用 LangGraph 不会自动提高检索准确率。

## 总路线

~~~mermaid
flowchart TD
    A["基础 RAG：检索与来源"] --> B["小型评估：找到当前问题"]
    B --> C["LangGraph：状态、节点、边"]
    C --> D["工具循环：手动理解 ReAct"]
    D --> E["Agentic RAG：分支与有限重试"]
    E --> F["记忆、流式输出、人工确认"]
    F --> G["接口、部署、日志与回归"]
    G --> H["按需拓展：MCP、子图、多 Agent"]
~~~

可以一边补 RAG 的检索效果，一边学基础图。完成整个高级 RAG 教程不是开始 LangGraph 的前置条件。

## 阶段一：让基础 RAG 能被检查

### 学习范围

- 文档清洗、分块大小与重叠。
- 保存 source、chunk_id 等来源信息。
- Embedding、top-k、元数据过滤。
- 无相关资料时的回答行为。
- 小型测试集与错误分类。

### 动手任务

准备约 20 个问题，包含直接查询、同义表达、跨片段问题和资料中没有答案的问题。人工标注预期来源与关键答案，每次修改后重复检查。

先观察：找没找到资料？资料是否足够？回答有没有超出证据？一次调用耗时和工具次数是多少？

根据错误再选一个改进方向：混合检索、重排或查询改写。固定问题集并逐项对比，避免同时替换所有组件。

### 完成标准

能拿出几组失败案例，说明失败发生在检索还是生成，并展示一次改进前后的对比。

资料：[All-in-RAG](https://github.com/datawhalechina/all-in-rag)，优先看文本分块、检索优化和评估章节。知识图谱和多模态部分留到有相应数据需求时。

## 阶段二：LangGraph 基础

### 学习范围

- State：本次流程需要携带的数据。
- Node：做一件事的函数。
- Edge：下一步去哪里。
- StateGraph、START、END。
- compile 与 invoke。
- 条件边和有限循环。
- 状态更新与 reducer。

### 动手任务

先写普通 Python 函数，再将它们串成一个不调用模型的小图。之后把已有 RAG 改成：

~~~text
问题 → 检索 → 生成 → 结束
~~~

### 完成标准

能自己增加节点、改变分支，并说明每个节点读取和更新了哪些字段。

[开始分步练习](langgraph-study-guide.md)

## 阶段三：用图理解 ReAct 工具循环

### 学习范围

- AIMessage.tool_calls 与 ToolMessage。
- bind_tools 负责让模型生成工具调用请求。
- ToolNode 执行工具，tools_condition 判断是否需要执行工具。
- MessagesState 与 add_messages。
- 结束条件与运行步数限制。

### 动手任务

用一个检索工具搭建：

~~~text
模型节点 → 有工具请求？ → 工具节点 → 模型节点
                     ↘ 无工具请求 → 结束
~~~

观察一次“模型要求检索”和一次“模型根据结果回答”，把参数、结果和消息顺序记录下来。实际轮数取决于模型行为。

### 完成标准

理解 LangChain create_agent 已经提供的循环，并能用低层节点描述相同结构。实际业务可以继续使用 create_agent，手写一次图主要用于理解和学习自定义流程。

## 阶段四：做一个可控的 Agentic RAG

### 动手任务

在同一个学习资料助手上添加：

1. 按问题选择直接回答或查询知识库。
2. 检索结果不足时，允许改写问题后再查一次。
3. 改写达到上限后结束，并说明证据不足。
4. 答案保留可核验来源。
5. 日志记录执行路径和检索次数。

### 实现提醒

- 检索节点、证据判断节点、改写节点、生成节点各自承担一个清晰职责。
- 判断节点可以使用规则，也可以使用模型结构化输出，先选容易验证的方法。
- retries 字段显式计数；recursion_limit 是图执行步数的保护上限，两者用途不同。
- 用相同测试问题对比基础 RAG 与新流程，检查额外耗时、调用成本和错误。
- 更复杂的流程可能产生更多错误，需要实验验证收益。

### 完成标准

能展示：一次成功检索、一次改写成功、一次到达重试上限的路径，并解释为什么结束。

## 阶段五：记忆、流式输出和人工确认

### 学习范围与练习

| 能力 | 要解决的问题 | 动手验收 |
| --- | --- | --- |
| Checkpointer 与 thread_id | 多次调用怎样接着同一会话运行？ | 同会话能继续，另一个会话独立 |
| 消息裁剪、摘要 | 历史越来越长怎么办？ | 对比摘要前后的事实保留与 token 消耗 |
| Store 与用户记忆 | 不同会话怎样共享用户偏好？ | 用户 A 的偏好不会串到用户 B |
| stream/astream | 怎样看到节点进展与模型增量输出？ | 分清节点更新与模型 token 输出 |
| interrupt 与 Command(resume=...) | 怎样等待人确认后继续？ | 同意、拒绝两条路径均可解释 |
| Runtime context | 用户身份、配置怎样传给节点？ | 能区分流程状态与本次运行依赖 |

学习人工确认时，可以使用“审核学习总结”的本地例子，确认后只打印结果。先把暂停和恢复机制看明白。

## 阶段六：将项目做成服务

Java 后端与 Agent 学习可以继续并行。Agent 服务这一轮练习：

- FastAPI 接收请求、校验参数、返回错误。
- /chat、创建会话、查询历史等接口。
- 服务端校验会话与用户的归属关系。
- 超时、有限重试、工具异常和调用日志。
- SQLite 或 PostgreSQL 的持久化；进程内 InMemorySaver 用于练习。
- 简单 SSE 流式响应和客户端断开处理。
- 环境变量、依赖固定、Docker 与启动说明。

也可以后续选择 LangGraph API 的运行方式。先完成一种清晰可解释的服务架构，避免同时学习两套服务接口。

完成标准：另一程序能调用；重启后的行为符合持久化设计；请求失败能定位；按照 README 能在另一环境启动。

## 阶段七：评估与可观测性

从阶段一的小型测试集开始，持续记录：

- 检索是否找到预期证据。
- 答案是否有证据支持。
- 是否选对工具，参数是否合理。
- 是否在预算内结束。
- 耗时、调用次数和费用。
- 错误发生在哪个节点。

先用自己的记录与人工判断，再按需要使用 LangSmith tracing、Ragas 等工具。模型评分也可能出错，重要失败案例应人工复核。把开发时调参的问题与最终验收问题分开。

## 阶段八：MCP、子图与多 Agent，按需继续

| 主题 | 学到什么程度 | 适合的小练习 |
| --- | --- | --- |
| MCP | 理解 host/client/server、工具发现、调用与传输方式 | 本地启动计算工具服务，客户端调用，再接到 Agent |
| 子图 | 封装可复用的检索或审核流程，定义输入输出 | 把检索流程封装成子图 |
| 并行与 Send | 动态分发任务、汇总结果、理解 reducer | 多个独立问题分别检索后汇总 |
| 多 Agent | 角色分工、上下文隔离、交接与总预算 | 检索员与总结员，并与单 Agent 比较 |
| Deep Agents | 理解规划、文件存储、上下文管理与委派 | 阅读一个研究助手示例，替换为自己的学习资料任务 |

LangGraph 的“图”描述程序执行关系；知识图谱 RAG 的“图”描述实体关系，二者概念不同。

MCP 接入按项目版本选择 SDK。整理时旧 langchain-mcp-adapters 仓库已归档并提示迁移，详见[资料清单](advanced-resources.md)。

## 建议保留的项目成果

尽量迭代同一个学习助手，保存每个阶段的代码或标签：

- v1：基础 RAG，有来源。
- v2：LangGraph 固定流程。
- v3：工具循环与有限查询改写。
- v4：持久化、流式输出与人工审核。
- v5：接口、部署与评估记录。

每个阶段都写清楚新增功能、一次失败案例、如何改进与验证。对实习面试而言，这些具体证据有助于说明自己的工程经验。
